# AI Agent 框架安全运行时：项目方向与架构原则

## 1. 项目长期方向

本项目的长期定位是：**与 Agent 开发框架协同工作的安全控制与审计层**。它通过框架适配器接入 Agent 应用，在模型调用、工具执行、数据访问和结果返回等边界执行可配置的安全检查，并生成可追溯的安全事件与审计发现。

本项目不替代 LangChain、LangGraph、CrewAI 或用户自己的 Agent 编排框架，而作为它们的安全伴生包（security companion package）：Agent 框架负责编排和调用；本项目负责定义/评估安全策略、在集成边界执行决定，并记录审计证据。

后续架构和功能开发应以本文件为方向基线。新功能应能说明它服务于哪个 Agent 生命周期边界、由哪个可信组件执行、需要什么事件/上下文、失败时如何处理，以及如何测试和审计。若功能与此方向不一致，应先讨论并更新本方向文档，而不是悄然扩成无关的通用安全工具集。

## 2. 管控边界与安全承诺

本项目可以管控 Agent 应用与外部能力之间的交互边界，包括模型请求前后、工具调用前后、数据读写与外发，以及相关策略和审计流程。它不能保证改变或控制模型内部的推理过程，也不能仅凭模型输出证明身份、授权或审批。

“管控大模型”在本项目中的准确含义是：

- 控制哪些上下文和数据可以发送给模型；
- 检查并约束模型生成的结构化响应和工具调用提议；
- 在可信执行点决定工具调用是允许、拒绝、需审批、需转换还是升级处理；
- 过滤或限制工具结果进入后续模型上下文或返回用户；
- 记录策略决定和执行结果，支持追踪与复核。

运行时强制控制必须位于实际副作用之前的可信执行边界，例如工具网关或服务端中间件。仅事后分析日志属于审计能力，不得宣传为调用拦截或完整安全保证。

## 3. Agent 生命周期控制点

### 3.1 模型调用前（Before Model Call）

适配器或宿主应用在提交模型请求前提供上下文，安全层可执行：

- 依据可信主体、租户、会话和策略版本检查请求上下文。
- 检查系统允许使用的模型、工具集合及其权限范围。
- 按数据分类策略执行最小化、脱敏、拒绝或人工审批要求。
- 保留输入数据的来源/信任标记，区分用户输入、检索结果、工具结果和系统策略。
- 生成请求关联标识，并记录实际采用的策略版本。

安全层不应将不可信上下文提升为策略或授权依据，也不应默认把全部检索数据、记忆或工具描述发送给模型。

### 3.2 模型响应后（After Model Response）

模型响应进入 Agent 执行流程前，安全层可执行：

- 结构、类型、大小和允许格式校验。
- 对敏感信息、超范围输出和策略禁止内容进行检测、脱敏或拒绝。
- 将模型生成的工具调用视为“提议”，而非已授权指令。
- 对不确定或高风险输出要求审批或升级给人工。
- 记录模型/提供方引用、策略版本、响应状态和关联请求 ID；不得记录不必要的敏感原文。

### 3.3 工具调用前（Before Tool Execution）

这是首个 MVP 的核心强制边界。任何工具执行前，统一安全入口应检查：

- 可信 Agent/主体身份、角色、租户和会话上下文。
- 工具是否已注册、是否允许当前主体调用。
- 动作和资源范围是否授权；参数 schema、大小、类型和业务限制是否符合策略。
- 目标地址、数据范围、预算/频率等是否在批准范围内。
- 操作是否敏感，是否存在可验证、未过期且范围匹配的审批。
- 是否应返回安全决策：`ALLOW`、`DENY`、`REQUIRE_APPROVAL`、`TRANSFORM` 或 `ESCALATE`。

执行层必须根据决策采取动作：`DENY` 不执行工具；`REQUIRE_APPROVAL` 暂停待可信审批；`TRANSFORM` 只应用明确配置的确定性变换后再重新校验；`ESCALATE` 转到指定人工/上级流程。不能把这些值仅当日志标签。

工具执行入口还应防止在检查后、执行前关键参数被替换；审批应绑定主体、工具、动作、资源和关键参数/范围。拒绝及审批等待必须在副作用发生前生效。

### 3.4 工具返回后（After Tool Result）

工具完成后、结果重新进入模型上下文或返回用户之前，可执行：

- 结果格式、大小、来源和状态校验。
- 敏感字段筛选、脱敏和数据最小化。
- 对不可信工具数据/网页内容保留来源标签，不将其解释为系统策略或审批指令。
- 检查结果是否允许传入下一轮模型、其他工具或外部输出。
- 记录真实执行状态、结果类别和副作用引用；避免将授权通过误报为工具执行成功。

### 3.5 记忆、检索与外部服务（后续阶段）

后续可在记忆写入、检索读取、向量库、文件系统和外部 API 边界接入相同策略上下文。每种集成应提供明确的数据来源、访问主体、目的地和执行结果，并定义不可用时的安全行为。这些能力不属于首个运行时 MVP 的默认承诺。

## 4. 统一决策模型

安全引擎对一次检查返回结构化决策，而不是仅返回布尔值：

- `ALLOW`：允许指定的动作继续。
- `DENY`：拒绝动作，执行层必须保证不发生副作用。
- `REQUIRE_APPROVAL`：暂停动作，等待可信审批；未审批前不执行。
- `TRANSFORM`：应用明确列出的确定性转换（例如字段最小化），变换后重新校验。
- `ESCALATE`：交由人工或上级策略流程处理。

决策对象至少包含：决定、稳定原因代码、规则 ID、策略版本、请求/事件 ID、适用主体和操作引用、可选的审批需求、建议处置，以及安全的诊断信息。不得在结果中回传秘密或敏感原文。

失败策略应按控制点显式配置并测试。执行前授权和高风险操作默认采用拒绝或暂停；离线审计和非强制分析可以采用“报告但不阻断”模式，但输出必须清晰标记为观察模式。

## 5. 建议架构与模块责任

首期优先保持现有 `ai_security_protocol` 导入路径，分层整理，避免为了架构图一次性创建大量空模块。随着职责稳定，可逐步拆分为：

```text
src/ai_security_protocol/
  core/
    context.py       # 可信 Agent/会话/请求上下文
    policy.py        # 策略与版本
    decisions.py     # 统一决策类型
    engine.py        # 框架无关的规则评估
  runtime/
    guard.py         # 通用调用前/调用后安全检查
    tool_guard.py    # 工具执行前控制及结果检查
    model_guard.py   # 模型请求/响应检查（后续）
    data_guard.py    # 数据最小化、敏感数据与输出检查（后续）
  events/
    models.py        # 标准化事件/审计发现
    audit.py         # JSONL 和离线审计
  adapters/
    base.py          # Agent 框架适配器协议
    <framework>.py   # 具体框架可选适配器
  cli.py
```

职责约束：

- `core` 不依赖特定 Agent 框架、Web 框架或模型厂商。
- `runtime` 提供调用边界 API；核心决策与实际工具执行应分开，确保宿主明确处理决策。
- `adapters` 只负责把框架 hook/context 转为统一协议，不应复制策略逻辑。
- `events` 负责结构化事件和离线审计；审计分析与运行时执行控制是两个能力，必须可分别使用。
- 框架 SDK 等依赖应作为可选安装 extras，基础包保持轻量。

上面的目录是目标架构，实际实施应按阶段抽取现有代码，不要求第一版一次性创建全部文件。

## 6. 适配器合同

每个 Agent 框架适配器应实现/映射以下能力：

1. 提供可信上下文：Agent/会话/请求标识、主体引用、租户/环境、策略版本或可信身份引用。缺失的身份信息不得由模型输出补齐。
2. 在模型调用前、模型响应后、工具执行前及工具返回后映射本项目的 hook；适配器须说明具体覆盖了哪些 hook、哪些未覆盖。
3. 工具执行前，将工具名和参数交给统一 guard，等待决策；只有 `ALLOW` 或完成审批/转换后重新允许的决策才可进入真实执行。
4. 记录工具真实执行状态、异常和结果，不把“调用提议”“授权决定”“工具执行”混为一条状态。
5. 统一映射框架事件，同时保留原始框架事件引用以便追踪；敏感原文默认不复制到审计事件。
6. 对框架不支持的 hook 或无法保证执行前拦截的路径，必须明确标注能力缺口，并提供降级/失败行为，不能暗示完整覆盖。
7. 每个适配器应有框架版本兼容范围、安装 extra、最小示例、单元/集成测试和升级兼容说明。

## 7. 标准事件与安全上下文

运行时事件应区分事件阶段，建议至少支持：

- `model.request.proposed`
- `model.request.checked`
- `model.response.received`
- `model.response.checked`
- `tool.call.proposed`
- `tool.call.decided`
- `tool.execution.started`
- `tool.execution.completed`
- `tool.execution.failed`
- `tool.result.checked`
- `approval.requested`
- `approval.completed`
- `security.finding.raised`

事件共通字段建议包括 `event_id`、`request_id`、`session_id`、`timestamp`（含时区）、`agent_id`/可信主体引用、`stage`、`operation`、`resource`、`decision`、`reason_code`、`policy_id`/`policy_version`、`execution_status` 和证据引用。敏感内容默认使用脱敏值、分类标签或不可逆引用，除非应用明确配置了合规的数据留存方式。

事件至少应区分：

- 模型/Agent 提出的动作；
- 安全引擎的决策；
- 宿主框架实际执行的结果；
- 离线审计基于日志得出的发现。

## 8. 首个运行时 MVP 范围

### 必须交付

1. 稳定的框架无关请求/事件上下文和安全决策模型。
2. 可配置的策略引擎，至少支持主体/角色、工具、动作、资源及默认拒绝规则。
3. 工具执行前 guard API；拒绝时能保证调用方不会执行工具。
4. 高风险动作的审批需求决策接口。MVP 可定义审批接口/引用模型，不自行假设已集成某种审批产品。
5. 结构化决策和安全事件输出，并与现有 JSONL 离线审计衔接。
6. 一种 Agent 框架适配器作为试点；在确认首个目标框架前，核心保持框架无关，不同时承诺多个适配器。
7. 测试证明允许调用进入执行、拒绝调用不进入执行、审批等待不会提前执行、执行错误与决策状态可区分。
8. README/示例清楚标明安装方式、可覆盖 hook、已知缺口和安全边界。

### 明确不纳入首个运行时 MVP

- 控制模型内部推理或保证模型服从指令。
- 自动阻止一切 Prompt Injection、内容违规或未知语义风险。
- 未经接入的工具、网络、模型调用、记忆或数据存储的强制保护。
- 完整身份提供方、密钥管理系统、审批系统或 SIEM 的实现。
- 多 Agent 框架全面兼容、管理后台、云端策略服务或企业控制台。
- 通过静态 JSONL 审计声称已实现运行时拦截。

## 9. Python API 与执行安全

预期 API 应体现“决策—执行分离”，例如：

```python
from ai_security_protocol import SecurityRuntime, ToolCall

runtime = SecurityRuntime(policy=policy)
call = ToolCall(
    agent_id="support-agent",
    tool_name="read_ticket",
    arguments={"ticket_id": "T-123"},
    request_id="req-456",
)

decision = runtime.before_tool_call(call)
if decision.action == "ALLOW":
    result = execute_tool(call)
    checked_result = runtime.after_tool_call(call, result)
elif decision.action == "DENY":
    raise PermissionError(decision.reason_code)
elif decision.action == "REQUIRE_APPROVAL":
    raise ApprovalRequired(decision.approval_ref)
```

此片段是目标接口草图，不代表当前包已提供这些类型。实际 API 设计必须确保框架适配器不能意外忽略拒绝结果；重要调用链的运行时模式应当失败关闭，不能只在 finally/异步回调中记录违规。

## 10. 测试与质量要求

### 核心单元测试

- 同一策略下允许、拒绝、审批、转换和升级决策的确定性测试。
- 缺少可信主体、策略加载错误、参数类型错误和策略版本缺失的测试。
- 工具调用拒绝时，fake tool 的执行计数必须仍为零。
- 审批待定时工具不执行；审批绑定参数变化时重新评估。
- 结果检查发生在返回模型/用户之前，且不会泄露未授权字段。
- 事件顺序和请求关联正确，决策允许与执行成功状态分开。
- 审计事件中敏感字段脱敏；异常信息不含凭据。

### 适配器集成测试

- 使用目标框架的真实 hook 生命周期验证覆盖点。
- 验证同步/异步工具、工具异常、取消、重试和并发情况下的执行顺序。
- 验证框架升级/不支持 hook 时显式失败或安全降级。
- 验证可选 extra 安装和框架不安装时基础包仍可导入。

### 发布门槛

- 单元和集成测试通过。
- 可从干净环境安装、导入、运行示例。
- 包含兼容性矩阵、已知限制、安全边界和变更日志。
- 不以“未发现 finding”承诺整个 Agent 或模型安全。

## 11. 分阶段路线图

### 阶段 0：当前代码与接口收敛

修复/核实现有包模块边界和测试，保留 JSONL 离线审计能力；定义统一 finding 和 event schema，避免 CLI 与核心逻辑混在一起。

### 阶段 1：框架无关安全核心

定义 `SecurityContext`、`ToolCall`、`Decision`、`Policy`、`SecurityEvent` 和稳定原因代码；实现确定性策略评估与工具前置 guard API。

### 阶段 2：工具调用运行时控制

将 guard 放在一个目标 Agent 框架的真实工具执行边界；以集成测试证明拒绝不会调用工具，审批等待不会提前执行，事件能完整关联。

### 阶段 3：输出与数据边界

增加模型输入/输出和工具结果检查接口；以明确可测试的规则实现字段最小化、脱敏或拒绝，避免承诺模型语义安全。

### 阶段 4：扩展与治理

根据用户需求增加其他框架适配器、审批/日志后端、策略加载和发布治理；每个扩展保持可选依赖，并有单独的兼容矩阵和验收测试。

## 12. 项目方向的变更原则

未来功能规划优先级按以下顺序：

1. 运行时关键边界的强制控制与安全失败行为；
2. 可追踪的事件、审计和证据完整性；
3. 框架适配和开发者体验；
4. 数据保护与模型输入/输出控制；
5. 企业级管理和额外扩展。

新功能必须有需求、信任边界、威胁/失败场景、测试和验收标准。任何涉及“阻断”“授权”“可信”“安全”的描述必须明确其实际执行点及证据，不能把建议性扫描或事后审计说成强制防护。
