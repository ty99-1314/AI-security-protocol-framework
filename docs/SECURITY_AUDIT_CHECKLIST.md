# AI Agent 安全审计清单（逐项细化）

> 本清单按用户确认的顺序逐条细化。当前版本已补充第 2 条“身份验证与授权审计”，并继续补充第 3 条“通信安全审计”。第 4—7 条将在逐条讨论、确认后再补充。本文是后续���现需求，不代表这些控制已经在项目中实现。

## 1. 审计基本信息

每次审计至少记录以下信息：

- 审计编号、审计日期、审计负责人及系统负责人。
- 被审计系统、环境、版本，以及纳入/排除的 Agent、工具和服务范围。
- 使用的身份、授权和审批策略名称及版本。
- 检查方法、样本范围、执行环境及证据引用。
- 每个检查项的状态：`通过`、`不通过`、`未验证`、`不适用`。
- 发现项、风险等级、整改负责人、计划完成日期及复核结果。

证据不足时必须标记为“未验证”，不得默认通过。`不适用`应记录理由和批准人。

# 2. 身份验证与授权审计

## 2.1 目标与边界

确认每个 Agent 或工作负载都能被可靠、唯一地识别；凭据的签发、使用、轮换和撤销受控；权限遵循最小权限并由可信执行端实施；高风险操作受到审批或额外限制。

审计需区分以下概念：

- **身份认证（Authentication）**：确认调用方是谁。
- **授权（Authorization）**：确认该身份是否可以对特定资源执行特定动作。
- **审批（Approval）**：对某次高风险操作进行额外的人类或流程确认；审批不能替代身份认证与授权。
- **事后审计（Audit）**：分析已产生的记录；不能替代调用执行前的认证或授权拦截。

本项目后续实现可检查事件、配置或审计证据，但不能仅凭 Agent 自报的 `agent_id`、`role` 或 `approved` 字段证明其真实性。身份声明及审批状态应来自可信认证/审批上下文，或由可信执行层签名、关联后再供审计使用。

## 2.2 审计对象与信任边界

开始检查前列出并绘制相关组件和信任边界：

- Agent 实例、运行工作负载、服务账号及其部署环境。
- Agent 调用的工具、API、数据库、文件存储和其他服务。
- 身份提供方、凭据签发方、密钥/秘密管理系统。
- 策略决策点（PDP）与策略执行点（PEP），如工具网关或服务端中间件。
- 高风险操作的审批系统、审批人和审批记录存储。
- 集中日志系统，以及 Agent、网关和资源服务之间的身份上下文传递路径。

每条身份或授权链路应能回答：身份由谁签发、谁验证、授权策略由谁决定、在哪个组件执行、失败时如何处理、相关证据存在哪里。

## 2.3 检查项 A：身份唯一性和身份来源

### 需求

1. 每个 Agent 实例、工作负载或服务主体应有稳定且可区分的标识；应说明标识是实例级、服务级还是部署级，避免不同含义混用。
2. 身份应由可信身份系统或受控部署流程建立，不应由不可信用户输入、提示词、工具参数或 Agent 自行声明后直接采信。
3. 身份凭据应绑定到明确主体，并限制其适用的环境、受众、服务或用途，避免开发环境凭据被生产服务接受。
4. 共享身份应有明确、经批准的例外理由、使用范围和补偿控制；优先使用可追溯到单个工作负载或调用者的身份。
5. 对身份提供方不可用、身份缺失、主体不匹配或凭据无法验证的情况，应定义安全处理方式；不得静默降级为匿名或默认高权限身份。

### 审计证据

- Agent/工作负载身份清单及其所有者、用途、环境和状态。
- 身份系统配置、身份签发流程、可信身份属性说明。
- 一条代表性调用的认证上下文链路：凭据由谁签发、哪个服务验证、验证结果如何传给工具执行端。
- 共享身份例外记录，以及匿名/无身份调用的配置和日志。

### 验证测试

- 分别使用有效身份、缺少身份、伪造/未知身份和错误环境身份进行授权测试。
- 确认身份缺失、无效或来源不可信时，敏感调用不会继续执行，并产生可追踪的拒绝记录。
- 确认不同 Agent 的事件不会因共用标识而无法区分责任主体。

### 判定条件

- **通过**：身份有可信来源，主体可区分，服务端能验证；异常身份不能绕过检查。
- **不通过**：只依赖请求字段或 Agent 自报身份；多个主体无法区分；无效身份能调用受保护资源。
- **未验证**：无法取得身份签发/验证配置或无法执行验证测试。

## 2.4 检查项 B：认证凭据安全与生命周期

### 需求

1. 每种凭据应有责任人、用途、允许的受众/服务、有效期和轮换方式。
2. 凭据应存放于受控的秘密管理设施或等价安全存储，不得硬编码在源码、镜像、示例配置、提示词、测试数据或日志中。
3. 应限制凭据读取权限，并记录凭据管理操作；运行时不得将秘密暴露给无关 Agent、工具或用户。
4. 应有签发、分发、续期、轮换、撤销、过期和紧急泄漏响应流程；轮换后旧凭据应在规定时间内失效。
5. 凭据应采用适合风险的有效期和权限范围；长期凭据如确实必要，应有书面例外、加强监控和轮换要求。
6. 证书、令牌、密钥等不同凭据类型应定义验证规则，明确签名/信任链、有效期、受众及撤销状态的检查责任。
7. 密钥和秘密不得通过错误消息、调试输出、异常堆栈或审计事件明文输出；审计证据应脱敏且仍可识别涉及的凭据记录。

### 审计证据

- 凭据类型与用途清单、有效期和轮换策略。
- 秘密管理系统的访问控制、轮换记录和读取审计记录。
- 泄漏响应流程及最近一次轮换/撤销演练或记录。
- 仓库、构建产物和日志的秘密扫描结果及其处置记录。

### 验证测试

- 对过期、已撤销、签名/证书无效、受众不匹配的凭据验证拒绝行为。
- 抽样确认凭据轮换后旧凭据在设定期限内失效，新凭据可按预期工作。
- 检查认证失败的日志中不包含凭据内容。

### 判定条件

凭据存在硬编码、无法撤销或已撤销凭据仍可使用，应至少判为高风险不通过；不能证明凭据生命周期受控时标记为未验证。

## 2.5 检查项 C：授权策略、最小权限与默认拒绝

### 需求

1. 授权决定至少应依据可信主体、动作、资源及适用上下文；策略应明确角色/主体与动作/资源的对应关系。
2. 权限应按最小权限分配，限定资源范围、操作类型、环境和必要时段；不能仅依赖宽泛角色名推断所有权限。
3. 应明确区分只读、创建、修改、删除、导出、对外发送、付款、管理策略等动作；高影响动作不得与普通读取权限隐式捆绑。
4. 未明确允许的访问应按默认拒绝处理；策略缺失、解析错误、版本不匹配或策略服务不可用时的行为必须明确并经过风险评审。
5. 授权应在实际资源或工具执行之前由可信服务端/网关检查；仅在客户端、提示词或事后审计中检查不满足执行控制要求。
6. 策略应有版本、所有者、审批记录、生效时间和回滚方式；运行中的授权决定应能关联到当时使用的策略版本。
7. 应避免请求参数或 Agent 输出自行扩大授权范围，例如将资源标识替换为任意资源、改变目标租户或指定任意外部目的地。
8. 权限清单应与实际已部署工具和资源对照，识别未使用权限、孤儿权限、过宽通配符和生产/测试环境混用。

### 审计证据

- 当前生效的策略及版本、策略审批/变更记录。
- Agent 身份到角色、动作、资源范围的权限矩阵。
- 网关或资源服务的执行前决策日志，至少能体现主体、动作、资源、允许/拒绝结果和策略版本。
- 实际权限与岗位/Agent 用途的对应说明，以及定期权限复核结果。

### 验证测试

- 测试明确允许的调用、未列入策略的调用、越权资源、越权动作及跨环境调用。
- 测试策略缺失、语法错误、加载失败和决策服务不可用时是否符合批准的安全行为。
- 确认拒绝发生在副作用之前，并且结果可关联到调用和策略版本。
- 检查对资源 ID、租户 ID、动作名称和目标地址的篡改不会扩权。

### 判定条件

如果授权仅由 Agent 决定、未明确动作默认放行、或拒绝发生在副作用之后，应判为不通过。单纯由本项目审计器根据 `role/action/resource` 生成 `UNAUTHORIZED_ACTION`，只能作为审计发现，不能证明执行时已阻断。

## 2.6 检查项 D：高风险动作审批与职责分离

### 需求

1. 组织应定义高风险动作清单，至少评估删除、批量修改、敏感数据导出、对外发送、资金支付、权限变更和安全策略变更。
2. 对需审批动作，应明确审批人资格、审批数量、审批时限、拒绝/撤销流程和紧急例外规则。
3. 审批必须绑定到具体 Agent/主体、动作、目标资源、参数摘要或业务范围、目的地及有效时间；不能把一次审批解释为不限范围的长期授权。
4. 审批状态应来自可信审批系统或可信执行上下文。普通请求里的 `approved: true` 不能单独作为有效审批证明。
5. 审批后若主体、动作、资源、金额/范围、目的地或关键参数改变，应重新审批或重新校验审批绑定范围。
6. 发起操作者与审批者应在风险允许范围内分离；对紧急绕过应记录理由、授权人、时间和事后复核。
7. 执行端应校验审批仍有效、未撤销且尚未被不当重复使用；审批检查失败时不得继续执行受控动作。

### 审计证据

- 高风险动作分类与审批规则。
- 审批记录，包括审批主体、对象、动作、范围、结果、时间和关联请求 ID。
- 执行端对审批的验证日志，以及审批撤销和紧急例外记录。

### 验证测试

- 无审批、审批被拒绝、过期审批、已撤销审批、审批主体不匹配和参数变更后重放审批等情况应被拒绝或要求重新审批。
- 对合法审批验证其只能授权绑定的操作范围，不能授权其他 Agent 或资源。
- 验证紧急例外有审计记录并进入事后复核。

## 2.7 检查项 E：权限变更、撤销与定期复核

### 需求

1. Agent 新建、扩权、角色变更、工具增加、数据范围变化和环境迁移均应触发授权评估和审批。
2. Agent 下线、实例销毁、任务结束、负责人变更、人员离职或凭据泄漏时，应有撤销身份和权限的流程及完成时限。
3. 权限复核应按风险设置周期；高风险权限和长期未使用权限应优先复核。
4. 应记录权限授予、修改、撤销的申请人、审批人、变更前后差异、生效时间和执行结果。
5. 应识别失去所有者的身份、无人使用的凭据、孤儿账号以及不再需要的工具权限，并完成处置。
6. 撤权过程应覆盖身份提供方、网关缓存、服务端 ACL、令牌/证书和相关会话；应验证撤权传播延迟是否在可接受范围内。

### 审计证据与测试

- 入职/离职、Agent 上线/下线和权限变更流程。
- 定期权限复核报告及超期整改记录。
- 抽样撤销一个测试身份或凭据，验证所有相关入口在规定时限内拒绝后续请求。
- 检查凭据轮换或撤销后是否仍存在缓存令牌、长连接或备用账号绕过撤权。

## 2.8 检查项 F：身份与授权事件记录

### 必要审计字段

对认证、授权和审批相关事件，建议至少记录：

- `timestamp`：带时区的事件时间。
- `event_id` 或 `request_id`：用于唯一关联一次请求。
- `agent_id` / `principal_id`：由可信认证上下文解析出的主体标识。
- `credential_ref`：不可逆或脱敏的凭据引用，不记录秘密本身。
- `role`、`action`、`resource`：实际参与授权判定的主体角色、动作和资源。
- `decision`：认证/授权/审批的允许、拒绝或错误结果。
- `policy_id`、`policy_version`：实际使用的策略标识和版本。
- `approval_ref`：如适用，记录审批记录引用及其校验状态。
- `reason_code`：稳定、可检索的判定原因代码。
- `execution_status`：操作是否真正进入执行、完成或产生副作用；不能把授权允许等同于执行成功。

日志应避免记录令牌、密码、私钥或未经脱敏的敏感业务内容。记录本身应由可信执行组件产生，并保护访问和完整性。

## 2.9 建议的审计发现代码

以下是后续实例化时可采用的发现代码建议，不代表当前包已实现：

- `IDENTITY_MISSING`：事件或调用没有可验证主体。
- `IDENTITY_UNTRUSTED`：身份来自不可信声明或无法验证签发方。
- `IDENTITY_SHARED`：多个 Agent 共用身份且无批准例外或可追溯性不足。
- `CREDENTIAL_EXPIRED`：使用过期凭据。
- `CREDENTIAL_REVOKED`：使用已撤销凭据。
- `CREDENTIAL_EXPOSURE`：凭据出现在源码、配置、提示词或日志等不应出现的位置。
- `AUTHZ_DENIED`：授权策略拒绝该主体执行该动作/访问该资源。
- `AUTHZ_DEFAULT_ALLOW`：未匹配策略时系统放行，违背默认拒绝要求。
- `AUTHZ_ENFORCEMENT_MISSING`：找不到执行前授权检查的可信执行点，或证据不足。
- `PRIVILEGE_EXCESSIVE`：权限明显超过 Agent 职责或所需范围。
- `APPROVAL_MISSING`：受控动作缺少有效审批。
- `APPROVAL_SCOPE_MISMATCH`：审批与实际主体、动作、资源、参数或目的地不匹配。
- `APPROVAL_EXPIRED_OR_REVOKED`：审批已过期或撤销仍被使用。
- `ACCESS_NOT_REVOKED`：身份或权限应撤销但仍可使用。
- `AUTHZ_AUDIT_INCOMPLETE`：缺少策略版本、决策原因或请求关联字段，无法复核授权结果。

每条发现应携带证据引用、风险级别、���响范围、建议整改、责任人和复核状态。发现代码用于分类，不能替代事实证据和风险分析。

## 2.10 后续 Python 包实例化需求

### 配置对象

后续可在 `AuditPolicy` 或独立身份策略配置中表达：

- 可信身份来源/允许的身份提供方或主体范围。
- 主体、角色、动作与资源的授权规则。
- 默认拒绝行为及策略版本标识。
- 高风险动作集合和审批要求。
- 凭据有效期、撤销状态等可由事件或接入适配器提供的审计属性。
- 身份、授权、审批事件的字段映射，以适配不同网关和身份系统。

必须将“策略配置不匹配”和“线上执行点未实施策略”区分为不同检查结论；配置存在不等于控制已生效。

### 事件输入

审计 API 应接受可信执行层归一化的认证/授权事件，至少支持上述主体、动作、资源、决策、策略版本、请求关联字段；不应要求调用方把密码、令牌或密钥交给审计器。JSONL 解析应校验必填字段、字段类型、时间戳和无效记录，并指出错误行号。

### 输出要求

每条发现应有稳定代码、严重性、主体/请求引用、事件时间、证据来源、简短说明和可采取的整改建议。审计结果应同时区分：

- 检查到违反规则；
- 检查通过；
- 输入或证据不足，无法判断；
- 检查不适用。

不得把“未发现违规”表述为“身份系统安全”或“授权已被执行”。

### 最小测试用例

1. 有效且唯一的主体执行允许动作：不产生身份/授权违规。
2. 无身份、未知身份或身份签名无法验证：产生对应发现。
3. 请求声明的角色与可信身份上下文不一致：不得相信请求声明。
4. 未授权动作、未授权资源、跨租户资源和默认未匹配规则：报告拒绝或默认放行风险。
5. 过期、撤销、受众不匹配的凭据：产生对应发现。
6. 无审批、过期审批、已撤销审批、审批范围不匹配：报告审批违规。
7. 已撤权身份仍可调用或超过撤权时限仍有效：报告撤权问题。
8. 缺失策略版本、决策原因或请求关联字段：标记审计证据不完整。
9. 无效事件、错误时间戳或字段类型错误：报告输入错误且包含行号，不泄露凭据内容。
10. 对允许/拒绝结果的测试同时检查执行状态，避免把“授权允许”误判为“操作已成功”或把“事后报告”误判为“执行前阻断”。

## 2.11 本条验收标准

身份与授权审计模块的需求细化完成后，至少应满足：

- 身份认证、授权和审批概念及信任边界清晰分离。
- 有可配置的检查规则、事件字段、稳定发现代码和状态模型。
- 每项发现可以追溯到事件、策略版本和证据来源。
- 核心允许、拒绝、异常凭据、审批不匹配、撤权和证据缺失情形有测试用例。
- 文档清楚声明审计分析与运行时执行控制的边界，不声称未实现的能力。

# 3. 通信安全审计

## 3.1 目标与边界

确认 Agent 与工具、服务或其他 Agent 之间的通信在传输中得到保护，并且双方能够验证对端身份、消息来源与完整性，且关键通信不会被明文传输或重放攻击利用。

本章聚焦“通信链路安全”，不等同于应用层数据分类、运行时权限控制或日志可信性。

## 3.2 通信信任边界

审计前应明确网络区域、信任边界和通信对象：

- Agent 与内部工具/服务通信。
- Agent 与外部 API、外设、第三方服务通信。
- Agent 与其他 Agent 或中间件通信。
- 监控、日志、追踪系统和消息总线。
- 证书、密钥、网关和代理监听端点所在的位置。

审计应能回答以下问题：

- 谁向谁发消息。
- 消息是否被加密。
- 是否验证了对端证书和主机名。
- 是否防止重放、篡改和中间人攻击。
- 密钥和证书的信任来源、分发和撤销是否受控。

## 3.3 检查项 A：传输保密性与协议安全

### 需求

1. 敏感通信必须使用受支持的安全通信协议；明文 HTTP、未加密 TCP、未受控的 WebSocket、任意端口或未知协议应被识别并评估风险。
2. 对外部和内部通信，必须明确哪些数据类别允许进行哪种传输方式；高风险数据不得走明文或弱加密通道。
3. 传输层协议、TLS 版本、加密套件和证书握手策略必须符合组织策略和安全基线；已弃用支持应被标记为不通过。
4. 应明确所有通信端点的目的和权限，包括哪些服务允许访问哪类 Agent、资源和会话。
5. 若系统设计允许 TLS 退化、配置回退或忽略证书错误，应明确列出例外、批准者和风险说明；默认原则应为“失败关闭”。
6. 在消息传递过程中，不能仅依赖业务参数中的字段判断通信是否安全，必须核实实际网络协议、端点和证书配置。

### 审计证据

- 通信架构图、协议和端口清单、网关配置、TLS 配置及证书管理记录。
- 服务端和客户端的安全协议配置、TLS 版本和加密套件策略。
- 自动扫描结果、配置审查、漏洞管理记录及安全基线比对结果。

### 验证测试

- 使用受控的测试环境验证：明文数据传输被拒绝或受到告警；TLS 配置错误时连接被拒绝；弱加密套件或过期协议无法建立连接。
- 验证所有关键通信链路都通过 TLS 或等效安全通道，对无权限服务接口被明确拒绝。

### 判定条件

- 通过：敏感通信都走受控加密协议，配置满足基线，错误配置被拒绝。
- 不通过：明文传输敏感数据、未进行端点验证或存在弱加密/协议降级。
- 未验证：无配置证据、无法完成端点测试或未证明协议/证书状态。

## 3.4 检查项 B：对端身份验证与证书信任链

### 需求

1. 通信双方必须验证彼此身份，不应仅信任 IP、域名或客户端声明。
2. 证书管理必须包含签发、分发、校验、轮换、撤销和过期处理；证书链和根证书信任必须明确。
3. 对外部服务和内部服务应分别定义受信任证书来源、允许的签发机构和过期策略；不可信证书必须被拒绝。
4. 在名称校验中，应检查主机名、SAN、CN 及服务主体是否符合配置和部署要求，不应仅检查是否存在任意证书。
5. 证书失效、过期、撤销或与服务主体不匹配时，连接必须失败，并产生审计日志。
6. 证书信息应尽量用于识别主体，而非被当作单纯的“能不能连接”的标志；连接成功不等于消息已经被授权或可信。

### 审计证据

- 证书管理策略、证书状态列表、轮换和撤销记录。
- 服务端和客户端的信任配置、根证书、中间证书和 hostname 校验规则。
- 证书错误日志、握手失败记录和告警工单。

### 验证测试

- 使用过期证书、错误域名证书、未受信任根证书、撤销证书和无效 SAN 证书测试连接失败行为。
- 验证不同环境或不同服务的证书信任链与配置一致；错误的通信端点不被接受。

### 判定条件

任何“忽略证书错误”“接受任意证书”“允许自签名或错误主机名”都应视为高风险问题；仅仅提示“连接成功”不能表明对端身份可信。

## 3.5 检查项 C：完整性保护与消息篡改检测

### 需求

1. Agent 发送或接收的重要消息必须允许验证消息完整性，避免中间人篡改或传输错误导致被错误执行。
2. 在设计上，应区分“完整性校验”和“身份认证”：完整性保证消息未被篡改，不等于证明发送者身份是可信的。
3. 对高风险动作、控制指令、授权结果和敏感数据导出，宜采用加密传输、签名或完整性校验方案，并验证协议支持。
4. 关键消息应具备时间戳、请求 ID、随机数或等价防重放机制，防止旧消息被重复提交。
5. 若协议中存在重复发送、重放或消息覆盖行为，必须定义处理方式、默认拒绝策略和审计记录。
6. 应建立校验失败响应流程：完整性错误或签名无效时应拒绝处理，并记录失败原因及证据。

### 审计证据

- 协议说明、签名和完整性校验配置。
- 关键消息的签名校验日志、重放检测日志、传输状态和错误记录。
- 在受控环境下演练消息篡改、重复发送和过期消息的行为。

### 验证测试

- 修改消息内容、伪造签名、重放历史消息、将旧消息作为新的动作提交。
- 验证系统能拒绝并记录事件，不产生副作用。

### 判定条件

若仅有“哈希对比”但没有可信的密钥或签名来源，则不能视为可信身份控制；若存在重放漏洞或消息篡改不被拒绝，应判为高风险。

## 3.6 检查项 D：密钥与证书管理

### 需求

1. 密钥、证书和令牌应集中管理、受控访问和定期轮换；绝不能被随意嵌入到脚本、日志或配置文件中。
2. 要明确密钥/证书的生成、分发、更新、撤销、废弃和恢复流程；组织应保留审计证据。
3. 对外部 API、内部网关、消息队列和工具调用，应明确密钥角色、有效范围和最小权限原则。
4. 提供安全事故响应流程：发现密钥泄露后，必须有快速撤销、轮换、通知和回溯措施。
5. 证书和密钥应有对应负责人、存储位置和访问审批；访问日志应保留到指定期限。
6. 对多环境（开发/测试/生产）配置，应避免相同密钥跨环境使用，除非方案已批准并被充分评估。

### 审计证据

- 密钥和证书管理策略、权限记录、轮换和撤销日志。
- 构建产物和仓库扫描结果、配置文件检查结果。
- 关键服务的密钥使用日志和泄露事件响应记录。

### 验证测试

- 扫描仓库和构建产物，确认无秘密、私钥或硬编码证书。
- 触发密钥轮换和撤销流程，验证旧密钥失效且新密钥正常工作。
- 验证错误环境中的同密钥无法通过网络访问或跨服务验证。

## 3.7 检查项 E：错误处理与泄漏防护

### 需求

1. 通信失败、握手失败、证书错误和重放检测失败时，应返回受控的错误信息，不泄露系统的实现细节或密钥状态。
2. 错误、堆栈、日志和监控输出不能泄露证书内容、私钥、令牌、内部地址、网络拓扑或敏感配置。
3. 应定义统一的错误分类与处理规范，包括拒绝、重试、降级、告警和保留证据。
4. 对失败模式应有明确审计记录，确保事故响应能够定位是连接失败、认证失败、授权失败、完整性校验失败还是网络中断。
5. 对外部服务返回异常值、非标准状态码、超时、协议降级，以及跨环境访问失败，应采用安全默认值和严格的日志脱敏处理。

### 审计证据

- 错误处理设计文档、日志脱敏策略、告警和事故响应记录。
- 异常和错误事件的样本日志与复盘结论。

### 验证测试

- 触发错误配置、证书错误、连接中断、超时、无权限、签名失败等情况，并检查返回值与日志是否脱敏。

## 3.8 检查项 F：通信事件记录与审计能力

### 必要审计字段

通信相关事件至少应记录：

- `timestamp`、`request_id`、`agent_id`、`source`、`destination`、`protocol`、`port`/`route`。
- 身份/证书引用、会话标识或连接标识。
- 认证/握手/授权状态、TLS 版本、加密套件和状态码。
- 结果：成功、失败、拒绝、超时、重放检测触发、证书错误。
- 失败原因代码（例如 `TLS_CERT_INVALID`、`REPLAY_DETECTED`、`AUTH_FAILED`）。
- 对应的策略版本、服务端/客户端证书状态、关键日志索引。

日志必须避免直接记录敏感信息；若必须记录，必须脱敏并说明保留规则。

## 3.9 建议的审计发现代码

- `TLS_DISABLED`：敏感通道未启用安全传输。
- `TLS_WEAK_VERSION`：TLS 版本或套件低于要求。
- `CERT_INVALID`：证书无效、过期、未受信任或与主体不匹配。
- `CERT_EXPIRED`：证书过期且仍在使用。
- `HOSTNAME_MISMATCH`：域名/证书主体校验失败。
- `REPLAY_DETECTED`：消息重放或重复提交被识别。
- `MESSAGE_TAMPERED`：完整性校验失败。
- `SECRET_EXPOSED_IN_LOG`：日志或错误信息暴露了密钥、证书或敏感内容。
- `UNTRUSTED_ENDPOINT`：目标服务不在允许列表中或不受信任。
- `COMMUNICATION_AUDIT_INCOMPLETE`：缺少协议、握手状态或请求关联字段。

## 3.10 后续 Python 包实例化需求

### 配置对象

后续可新增或扩展 `AuditPolicy` 中的通信安全规则，例如：

- 允许的协议和最低 TLS 版本。
- 受信任的证书来源和域名约束。
- 允许的目标地址/端点和禁止列表。
- 是否要求消息签名、重放窗口和请求时效控制。
- 失败时的默认拒绝策略与日志保留需求。

### 输入事件

通信安全审计应处理标准化后的网络/会话事件，而非直接解析底层 TLS 报文。输入事件至少应包含：

- 来源、目标、协议、端口/路线。
- 证书或凭据引用、握手状态和结果。
- 时间戳、会话 ID、请求 ID 和策略版本。
- 失败原因（如 TLS、验证失败、重放检测）。

### 输出要求

对每条发现记录：

- 发现代码、严重性、来源/目的地、时间戳。
- 依赖的协议/证书/会话上下文。
- 简要说明与证据指向。
- 建议整改措施、责任人、复核要求。

### 最小测试用例

1. 明文敏感通信被识别。
2. TLS 版本过低或协议不符合策略：报告 `TLS_WEAK_VERSION`。
3. 证书过期、无效或域名不匹配：报告 `CERT_INVALID` / `CERT_EXPIRED`。
4. 消息篡改或签名无效：报告 `MESSAGE_TAMPERED`。
5. 重放请求被识别：报告 `REPLAY_DETECTED`。
6. 日志中出现证书/密钥/令牌：报告 `SECRET_EXPOSED_IN_LOG`。
7. 端点不在受信任列表：报告 `UNTRUSTED_ENDPOINT`。
8. 缺少协议、握手状态或请求 ID：报告 `COMMUNICATION_AUDIT_INCOMPLETE`。

## 3.11 本条验收标准

通信安全审计模块达到以下条件即可进入下一步实现：

- 明确覆盖协议安全、证书验证、完整性校验、消息重放防护、密钥管理和错误泄漏控制。
- 有受控的默认拒绝策略与失败处理流程。
- 发现逻辑可以与真实通信事件对接，并能追踪到证据来源。
- 关键高风险场景包括：明文传输、弱协议、证书错误、篡改、重放、泄密和端点越界。
- 文档明确说明：通信安全不是等价于身份授权，也不是日志可信性自动保证。
