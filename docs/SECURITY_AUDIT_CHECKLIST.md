# AI Agent 安全审计清单（逐项细化）

> 本清单按确认顺序逐条细化。当前已完成第 1、2、3、4、5 条的详细需求描述，并继续补充第 6 条“审计与日志审计”。后续第 7 条将按同样方式继续追加。

## 1. 审计基本信息

每次审计至少记录以下信息：

- 审计编号、审计日期、审计负责人及系统负责人。
- 被审计系统、环境、版本，以及纳入/排除的 Agent、工具和服务范围。
- 使用的身份、授权和审批策略名称及版本。
- 检查方法、样本范围、执行环境及证据引用。
- 每个检查项的状态：`通过`、`不通过`、`未验证`、`不适用`。
- 发现项、风险等级、整改负责人、计划完成日期及复核结果。

证据不足时必须标记为“未验证”，不得默认通过。`不适用`应记录理由和批准人。

# 2. 身份验证与授权审计

## 2.1 目标与边界

确认每个 Agent 或工作负载都能被可靠、唯一地识别；凭据的签发、使用、轮换和撤销受控；权限遵循最小权限并由可信执行端实施；高风险操作受到审批或额外限制。

审计需区分以下概念：

- 身份认证：确认调用方是谁。
- 授权：确认该身份是否可以对特定资源执行特定动作。
- 审批：对高风险操作额外确认；审批不能代替认证与授权。
- 事后审计：分析已产生的记录；不能替代调用前的认证或授权拦截。

不能仅凭 Agent 自报的 `agent_id`、`role` 或 `approved` 字段证明其真实性；应来自可信认证上下文或可信执行层签名。

## 2.2 审计对象与信任边界

需要明确：

- Agent 实例、运行工作负载、服务账号及其部署环境。
- Agent 调用的工具、API、数据库、文件存储和其他服务。
- 身份提供方、凭据签发方、密钥/秘密管理系统。
- 策略决策点（PDP）与策略执行点（PEP），例如工具网关或服务端中间件。
- 高风险操作的审批系统、审批人和审批记录存储。
- 日志系统，以及 Agent、网关和资源服务之间的身份上下文传递路径。

## 2.3 检查项 A：身份唯一性和身份来源

### 需求

1. 每个 Agent 实例、工作负载或服务主体应有稳定且可区分的标识。
2. 身份应来自可信身份系统或受控部署流程，不应直接信任 Agent 自声明。
3. 身份凭据要绑定到明确主体，并限制其适用环境和用途。
4. 共享身份必须有批准说明、范围和补偿控制。
5. 身份提供方不可用、身份缺失、主体不匹配等情况必须安全拒绝，而不是降级为匿名或高权限。

### 审计证据

- Agent 身份清单、环境、职责和所有者。
- 身份系统配置、签发和验证流程。
- 认证上下文链路：谁签发、谁验证、如何传给执行端。

### 验证测试

- 有效身份、缺失身份、伪造身份、错误环境身份的授权测试。
- 不可信身份不能继续访问敏感资源。

## 2.4 检查项 B：认证凭据安全与生命周期

### 需求

1. 每种凭据应有责任人、用途、有效期和轮换方式。
2. 凭据应存放在受控的秘密管理设施，不得硬编码在代码、配置、日志和提示词中。
3. 应限制凭据读取权限并记录管理操作。
4. 应有签发、分发、轮换、撤销、过期和泄漏响应流程。
5. 凭据有效期和权限范围应与风险匹配。
6. 证书、令牌、密钥等不同凭据类型应定义验证规则和撤销状态检查。
7. 密钥和秘密不能通过日志、错误消息和异常堆栈泄漏。

### 审计证据

- 凭据用途、有效期和轮换策略。
- 秘密管理系统的访问控制和轮换记录。
- 泄漏响应记录和秘密扫描结果。

### 验证测试

- 过期、已撤销、证书无效或受众不匹配的凭据必须被拒绝。
- 旧凭据轮换后失效且新凭据可正常使用。

## 2.5 检查项 C：授权策略、最小权限与默认拒绝

### 需求

1. 授权应依据可信主体、动作、资源与上下文。
2. 权限应按最小权限分配，避免宽泛角色导致越权。
3. 需区分只读、创建、修改、删除、导出、支付、管理等动作。
4. 未明确允许的访问应按默认拒绝处理。
5. 授权应在执行前由可信服务端/网关检查，而不是仅由客户端或日志审计做判断。
6. 策略应具备版本、所有者、审批和回滚方式。
7. 资源 ID、租户 ID 和目标地址不应被篡改扩权。

### 审计证据

- 生效策略及版本、审批和变更记录。
- 角色-动作-资源矩阵和权限复核记录。
- 执行前决策日志。

### 验证测试

- 明确允许、未列入策略、跨租户和越权动作测试。
- 策略缺失、错误或服务不可用时的安全行为检查。

## 2.6 检查项 D：高风险动作审批与职责分离

### 需求

1. 定义高风险动作清单，如删除、导出、支付、权限变更等。
2. 明确审批人资格、审批数量、审批时限、撤销和紧急例外规则。
3. 审批必须绑定到具体主体、动作、资源、目的地和有效时间。
4. `approved: true` 不能单独作为有效审批证明，必须来自可信审批系统或执行层真实上下文。
5. 关键参数变更后应重新审批。
6. 发起操作者与审批者应分离；紧急绕过应有记录和事后复核。
7. 执行端必须校验审批仍然有效、未被撤销并且范围匹配。

### 审计证据

- 高风险动作分类和审批规则。
- 审批记录和审批验证日志。

### 验证测试

- 无审批、过期审批、已撤销审批、参数不匹配时必须被拒绝或要求重新审批。

## 2.7 检查项 E：权限变更、撤销与定期复核

### 需求

1. Agent 新建、扩权、角色变更、工具增加和环境迁移应触发授权评估。
2. Agent 下线、离职、凭据泄漏时需要撤销身份和权限。
3. 高风险权限和长期未使用权限应定期复核。
4. 权限授予、修改和撤销记录必须完整。
5. 孤儿账号和不再需要的权限应被清理。
6. 撤权应覆盖网关缓存、ACL、令牌和相关会话。

### 审计证据

- 入职/离职、权限变更和撤销记录。
- 复核报告和整改记录。

### 验证测试

- 抽样撤销测试身份，验证所有入口都拒绝后续请求。

## 2.8 检查项 F：身份与授权事件记录

### 必要审计字段

- `timestamp`
- `event_id` / `request_id`
- `agent_id` / `principal_id`
- `credential_ref`
- `role`、`action`、`resource`
- `decision`
- `policy_id`、`policy_version`
- `approval_ref`
- `reason_code`
- `execution_status`

日志不能记录秘密；应脱敏处理。

## 2.9 建议发现代码

- `IDENTITY_MISSING`
- `IDENTITY_UNTRUSTED`
- `IDENTITY_SHARED`
- `CREDENTIAL_EXPIRED`
- `CREDENTIAL_REVOKED`
- `CREDENTIAL_EXPOSURE`
- `AUTHZ_DENIED`
- `AUTHZ_DEFAULT_ALLOW`
- `AUTHZ_ENFORCEMENT_MISSING`
- `PRIVILEGE_EXCESSIVE`
- `APPROVAL_MISSING`
- `APPROVAL_SCOPE_MISMATCH`
- `ACCESS_NOT_REVOKED`

## 2.10 后续 Python 包实例化需求

- 允许配置可信身份来源、角色-动作-资源规则和审批要求。
- 事件输入应来自可信执行层，不应要求审计器接收秘密。
- 输出应区分通过、拒绝、未验证、不适用。
- 最小测试应覆盖：有效主体、无身份、未知身份、过期凭据、缺失审批和撤权问题。

## 2.11 本条验收标准

- 身份认证、授权和审批概念及信任边界清晰分离。
- 有可配置的检查规则、事件字段和稳定发现代码。
- 可追溯到事件、策略版本和证据来源。
- 核心场景有测试用例，且文档明确说明审计分析和执行控制边界。

# 3. 通信安全审计

## 3.1 目标与边界

确认 Agent 与工具、服务或其他 Agent 之间的通信在传输中得到保护，并且双方能验证对端身份、消息来源与完整性。

## 3.2 通信信任边界

需要明确：

- Agent 与内部/外部服务通信对象
- 消息总线和日志链路
- 证书与密钥管理系统
- 端点、路由和网络区域

## 3.3 检查项 A：传输保密性与协议安全

### 需求

1. 敏感通信必须使用受支持的安全协议。
2. 明文 HTTP、未受控 WebSocket 或弱加密通道必须识别为风险。
3. TLS 版本、套件和证书握手策略必须符合基线。
4. 所有通信端点必须知道其目的和权限。
5. 默认行为必须是失败关闭，不允许忽略证书错误。

### 审计证据

- 通信架构、协议清单、TLS 配置和证书管理记录。

### 验证测试

- 明文传输、弱协议和过期 TLS 测试失败。

## 3.4 检查项 B：对端身份验证与证书信任链

### 需求

1. 通信双方必须验证彼此身份。
2. 证书链和根证书信任必须明确。
3. 域名、SAN 和证书主体必须校验。
4. 过期、撤销和错误主机名证书必须拒绝。

### 审计证据

- 证书状态、轮换和撤销日志。

### 验证测试

- 过期、错误域名、未信任根证书和撤销证书测试失败。

## 3.5 检查项 C：完整性保护与消息篡改检测

### 需求

1. 关键消息必须可校验完整性。
2. 不能把完整性误认为身份认证。
3. 关键动作、授权结果和导出数据应进行签名或完整性校验。
4. 应具备时间戳、请求 ID 和重放防护。
5. 完整性校验失败必须拒绝处理并保留证据。

### 审计证据

- 签名校验日志、重放检测日志和错误记录。

## 3.6 检查项 D：密钥与证书管理

### 需求

1. 密钥、证书和令牌应集中管理、受控访问和定期轮换。
2. 不得嵌入代码、日志或配置文件。
3. 应明确分发、更新、撤销和恢复流程。
4. 泄漏后必须快速撤销和轮换。

## 3.7 检查项 E：错误处理与泄漏防护

### 需求

1. 通信失败时返回受控错误，不能泄露内部实现细节。
2. 日志不能含私钥、证书或敏感配置。
3. 失败模式要记录到审计链路中。

## 3.8 检查项 F：通信事件记录与审计能力

### 必要审计字段

- `timestamp`
- `request_id`
- `agent_id`
- `source` / `destination`
- `protocol` / `port`
- `certificate_ref`
- `session_id`
- `handshake_status`
- `result`
- `reason_code`

## 3.9 建议发现代码

- `TLS_DISABLED`
- `TLS_WEAK_VERSION`
- `CERT_INVALID`
- `CERT_EXPIRED`
- `HOSTNAME_MISMATCH`
- `REPLAY_DETECTED`
- `MESSAGE_TAMPERED`
- `SECRET_EXPOSED_IN_LOG`
- `UNTRUSTED_ENDPOINT`

## 3.10 后续 Python 包实例化需求

- 增加通信安全规则：允许协议、最低 TLS 版本、可信证书来源、目标地址白名单等。
- 事件输入至少包含源、目的地、协议、握手和失败原因。
- 输出需说明发现代码、严重性、证据来源和整改建议。

## 3.11 本条验收标准

- 覆盖协议安全、证书验证、完整性校验、密钥管理和泄漏防护。
- 关键高风险场景包括明文传输、证书错误、篡改、重放和端点越界。

# 4. 行为约束与异常检测审计

## 4.1 目标与边界

确认 Agent 的动作受明确策略约束，高风险行为不能被随意执行，异常行为能被检测、告警和处置，并且所有策略更新都有审查与回滚能力。

## 4.2 行为控制的信任边界

审计前应明确：

- 哪些 Agent 允许执行哪些动作。
- 哪些动作属于高风险并需额外审批。
- 执行点在哪里。
- 发生拒绝时是否阻断副作用，以及是否保留审计证据。
- 哪些行为属于异常，如何被检测和上报。

## 4.3 检查项 A：策略定义与动作分级

### 需求

1. 明确角色-动作-资源矩阵。
2. 覆盖删除、导出、发送、权限提升和敏感数据访问等高风险动作。
3. 允许列表和拒绝列表概念明晰，默认行为必须定义。
4. 策略应具备版本管理和审批链路。

### 审计证据

- 策略文档、版本历史、审批记录和角色-动作-资源矩阵。

### 验证测试

- 允许动作、禁止动作、缺失审批动作和跨角色访问测试。

## 4.4 检查项 B：执行前拦截与默认拒绝

### 需求

1. 对高风险行为必须在工具执行前做决策。
2. 未命中策略、策略错误或服务不可用时必须按安全方式处理。
3. 对执行前决策应保留证据。
4. 仅“只记录不阻止”不等于安全控制。

### 审计证据

- 执行前决策日志、拒绝/允许记录和失败策略实现。

## 4.5 检查项 C：敏感动作与审批触发

### 需求

1. 敏感动作清单必须明确，包括导出、删除、支付和权限提升等。
2. 需要绑定到具体主体、动作、资源和范围。
3. 审批不能替代执行控制。
4. 紧急例外应有理由、授权人和复核。

## 4.6 检查项 D：异常行为检测与阈值管理

### 需求

1. 定义异常行为（如短时大量拒绝、异常频率、资源使用异常和可疑目的地）。
2. 阈值必须有依据，并能定期复审。
3. 异常检测结果应包含时间窗口、事件证据和风险级别。
4. 异常检测不等于执行阻断，需要对应的处置策略。

### 审计证据

- 告警规则、阈值定义和事件样本。

## 4.7 检查项 E：告警、响应、处置与事后复盘

### 需求

1. 告警应有接收人、优先级、升级路径和 SLA。
2. 响应过程必须记录处理人、时间和状态。
3. 处置动作必须可审计，如暂停 Agent、撤销权限等。
4. 需要有复盘和修正流程。

## 4.8 检查项 F：策略变更、审查与回滚

### 需求

1. 策略变更必须有审批、版本、部署时间和回滚方案。
2. 新策略需验证并能回滚。
3. 高影响策略应进行额外审查和审批。

## 4.9 建议发现代码

- `POLICY_MISSING`
- `POLICY_INCOMPLETE`
- `DEFAULT_ALLOW`
- `EXECUTION_NOT_BLOCKED`
- `SENSITIVE_ACTION_NO_APPROVAL`
- `ANOMALY_THRESHOLD_UNDEFINED`
- `ANOMALY_NOT_ALERTED`
- `POLICY_CHANGE_UNTRACKED`

## 4.10 后续 Python 包实例化需求

- `AuditPolicy` 增加允许动作、敏感动作、默认拒绝、阈值和告警处理。
- 事件输入至少包括动作、资源、目的地、决策和审批状态。
- 输出需记录发现代码、严重性、事件引用、是否已告警和是否已处置。

## 4.11 本条验收标准

- 能区分允许、禁止、敏感动作和强制审批动作。
- 能在执行前或执行中体现安全决策，不仅事后发现在日志中。
- 能对异常行为设置阈值、告警和处置流程。
- 能解释策略版本、决策结果和回滚方式。

# 5. 数据安全审计

## 5.1 目标与边界

确认 Agent 访问、处理、传输和存储的数据受到适当保护，敏感数据流不会被未经控制地扩散，数据外发、脱敏和生命周期管理都可验证。

本章重点关注“数据本身的安全”，而不是仅关注 Agent 是否做了某个动作。它要求审计者判断数据分类、访问边界、输出和存储处是否符合最小化和安全控制要求。

## 5.2 数据信任边界

审计前应明确：

- 哪些信息属于敏感数据、个人信息、业务机密或受监管数据；
- 哪些 Agent、工具、数据库、缓存和外部服务接触这些数据；
- 数据从哪里进入系统，流向哪里，是否被复制、导出、缓存或发送到第三方；
- 数据在在线、离线、日志、备份和测试环境中的存储和保护方式。

审计应回答：

- 数据为什么需要访问；
- 谁有权访问；
- 数据是否最小化；
- 是否能追踪其流转；
- 是否存在超范围导出或意外副本。

## 5.3 检查项 A：敏感数据识别与分类

### 需求

1. 系统必须明确识别哪些数据属于敏感、个人、机密或受监管数据。
2. 数据分类应覆盖输入、存储、缓存、日志、备份、模型上下文、工具参数、输出和导出。
3. 每类数据应有访问限制和最小化要求。
4. 不得仅凭“模型或 Agent 处理了该数据”就视其无需保护。
5. 需要定义数据的风险级别、访问方式和责任人。
6. 对高风险或受监管数据，应要求强制的访问控制与审计记录。

### 审计证据

- 数据分类表、数据流图、存储和访问控制清单。
- 受控数据清单、风险级别和处理要求。

### 验证测试

- 抽样检查高风险数据是否能被未授权 Agent 或工具访问。
- 验证不同数据类别在系统中的处理范围与文档一致。

### 判定条件

- 通过：数据有显式分类、最小化和访问边界。
- 不通过：敏感数据未分类、无访问限制、被过度复制或使用。
- 未验证：无法说明数据价值、数据流和保留规则。

## 5.4 检查项 B：最小访问与数据访问控制

### 需求

1. Agent 和工具只能访问完成任务所需的最小数据范围。
2. 读取、修改、删除、导出等权限都应按数据类别和业务需要单独控制。
3. 模型上下文、工具参数和返回值不应自动包含全部敏感数据。
4. 请求中出现大字段、全量数据或辅助信息时，必须检查是否强制截断或脱敏。
5. 对跨租户、跨部门、跨环境的数据访问应进行额外校验。
6. 长期持有的敏感数据缓存、索引、向量库或文件副本应按最小必要原则管理。

### 审计证据

- 权限矩阵、最小访问策略、数据访问日志。
- 访问控制配置、大文本字段截断策略和策略审查记录。

### 验证测试

- 验证 Agent 访问敏感数据时，是否只能访问授权范围内字段。
- 测试越权读取和跨资源访问是否被拒绝。

## 5.5 检查项 C：数据传输与存储保护

### 需求

1. 敏感数据在传输和存储过程中必须使用受控安全机制。
2. 数据传输不能仅依赖“某个应用调用了某个接口”，还必须核实协议、端点和密钥状态。
3. 数据存储必须区分在线存储、缓存、索引、备份和测试环境，且各自必须有适当保护。
4. 对外部服务、数据库、对象存储、日志和消息系统，应明确访问方式和加密要求。
5. 传输中的敏感数据不能出现在明文日志、错误信息、追踪记录或监控指标中。
6. 密钥和数据必须分离，不能用同一套凭据控制同时存储和读取敏感信息。

### 审计证据

- 存储配置、加密或脱敏策略、访问权限和日志脱敏规则。
- 传输安全配置和数据存储架构图。

### 验证测试

- 传输和存储中的敏感数据是否可被复现和复制，且是否受控。
- 触发异常日志情景，验证其不泄露真实敏感数据。

## 5.6 检查项 D：数据流追踪与外发控制

### 需求

1. 需要明确数据从输入、访问、处理、输出到存储和导出的链路。
2. 对数据导出、对外发送和第三方传递必须有明确控制和审批。
3. 必须验证导出目标是否可信、是否在允许范围内、是否附带审批记录和最小化输出。
4. 对外发前应进行字段级过滤、脱敏、分级和必要的业务校验。
5. 不能依赖事件中的 `destination` 字段单独判断是否安全，必须有可信端点验证。
6. 对外发动作要记录：发送对象、原因、数据范围、审批状态、时间和结果。
7. 外发数据、高风险结果和模型输出必须跟踪到对应调用和请求 ID。

### 审计证据

- 数据流图、外发审批记录、导出日志和目的地白名单。
- 外部服务接入清单与风险评估记录。

### 验证测试

- 测试外发到未知、公共、非白名单或未经审批的目标。
- 验证敏感字段被最小化或完全被过滤。

## 5.7 检查项 E：数据完整性与可信来源

### 需求

1. Agent 生成或改写的数据必须区分来源、可信度和校验状态。
2. 关键数据在进入高影响流程前应进行一致性、范围和来源校验。
3. 对外部输入、工具输出和用户输入，都要确认其是否可信、是否清洗和是否有必要的验证。
4. 对于模型输出、工具返回和中间计算结果，应防止其被当作“可信事实”直接用于敏感决策。
5. 需要对关键字段进行完整性、格式和合法性校验，避免提示词或输入污染安全逻辑。
6. 需要保留证据：哪些数据来自什么来源、如何被处理、最终如何被使用。

### 审计证据

- 数据来源清单、校验逻辑、完整性检查记录和执行状态记录。

### 验证测试

- 伪造、过期、格式错误、被篡改的数据进入系统时，是否被拒绝或进入受控处理。

## 5.8 检查项 F：日志、缓存、提示词与副本泄露防护

### 需求

1. 日志、缓存、提示词、检索索引、向量数据库和错误消息不能意外保存敏感信息。
2. 需要对日志字段、缓存键和模型上下文做最小化、脱敏和过期处理。
3. 对包含敏感信息的工具返回、模型输出和用户输入，必须定义哪些可以记录、哪些必须丢弃。
4. 必须保留清理流程，清除无效副本、过期缓存和临时文件。
5. 需要检查测试环境中是否存在生产敏感数据副本。

### 审计证据

- 日志脱敏规则、缓存清理策略、测试数据隔离记录、敏感信息扫描记录。

### 验证测试

- 触发错误消息、异常日志、缓存回收和示例输出，验证是否泄露敏感内容。

## 5.9 检查项 G：保留期限、删除与备份管理

### 需求

1. 系统必须定义数据保留期限、归档方式和删除流程。
2. 敏感数据副本（备份、缓存、日志、索引、镜像）应纳入同等管理。
3. 删除动作必须可验证，并覆盖未同步的副本。
4. 备份与恢复必须遵循最小权限和最小必要原则。
5. 数据生命周期策略应适用于测试、开发、生产和应急环境。

### 审计证据

- 保留政策、删除流程、备份审计和销毁记录。

### 验证测试

- 验证被删除数据在备份、缓存和日志中是否仍然可访问。

## 5.10 建议发现代码

- `DATA_UNCLASSIFIED`
- `DATA_OVER_ACCESS`
- `DATA_EXPORT_UNAPPROVED`
- `DATA_EXFILTRATION_RISK`
- `DATA_TAMPERED`
- `LOG_DATA_LEAK`
- `CACHE_DATA_LEAK`
- `DATA_RETENTION_MISSING`
- `DATA_COPY_UNCONTROLLED`
- `DATA_AUDIT_INCOMPLETE`

# 6. 审计与日志审计

## 6.1 目标与边界

确认 Agent 系统能够生成可信、可关联、可复核、可留存的安全审计记录，并且这些日志能支撑事件回溯、异常追踪、风险调查和合规复核，而不是仅作为定性说明或无结构文本。

本章重点关注“审计日志本身的可信性与可用性”，而不是单纯的应用行为检查。审计日志必须能够证明某一次操作发生了什么、谁做了什么、什么时候、怎么决定的、为什么被允许或拒绝，以及证据是否齐全。

## 6.2 审计日志信任边界

审计前应明确：

- 日志从哪个组件生成：Agent、工具网关、执行中间件、资源服务、审批系统、监控系统？
- 日志是否来自可信执行点，还是由调用方或模型自行写入？
- 日志访问权限控制是谁负责？是否防止内部人员修改、删除或覆盖？
- 日志是否可关联到请求 ID、会话 ID、策略版本、审批记录和执行结果？
- 日志留存的保密性、可用性和可追溯性要求是什么？

审计应能回答：

- 事件是否真实发生？
- 事件生成时具备什么上下文？
- 事件是否可证明与最终执行一致？
- 日志是否可作为证据用于复盘和责任追踪？

## 6.3 检查项 A：日志覆盖范围与事件完整性

### 需求

1. 日志必须覆盖关键事件，包括身份认证、授权决策、审批状态、执行状态、异常、拒绝、告警、撤权和事件修正。
2. 对所有高风险动作、敏感访问、外发动作、策略变更、异常触发和违规处理，都应有日志记录。
3. 日志必须包含稳定的事件标识，如 `timestamp`、`event_id`、`request_id`、`session_id`、`agent_id` 和必要的上下文字段。
4. 日志不能仅覆盖“成功行为”，还必须覆盖拒绝、错误、超时、重放和异常等失败事件。
5. 审计日志必须可证明“概念上的授权/审批状态”与“实际执行状态”是否一致；不能把“允许了”误认为“执行了”。
6. 缺失关键事件必须被标记为日志覆盖缺失，而不是默认为正常。
7. 日志字段应覆盖“谁、什么时候、访问了什么、为什么、结果如何”，而不是只留下部分简短状态。

### 审计证据

- 审计日志设计文档、字段清单、事件覆盖矩阵、关键执行路径日志。
- 关键事件的日志样本，能够回放到实际请求链路。

### 验证测试

- 生成一个授权拒绝事件、一个高风险动作审批事件、一个工具执行成功事件和一个失败事件，验证日志字段是否齐全。
- 检查是否存在事件缺失、字段空值、状态无法关联等问题。

### 判定条件

- 通过：关键事件都有稳定记录，字段齐全且可以关联。
- 不通过：核心事件缺失、日志不一致、状态混淆、无法证明真实执行。
- 未验证：无法确认关键日志从何而来、如何生成、何时写入。

## 6.4 检查项 B：时间戳、时序一致性与事件关联

### 需求

1. 所有审计事件必须带有带时区的时间戳，时间精度应足够区分同一毫秒/秒内的多个动作。
2. Log 时间、系统时间和处理时间必须区分，并明确其语义。
3. 事件之间应可用 `request_id`、`session_id`、`agent_id`、`approval_ref`、`policy_version`、`resource_id` 等字段关联。
4. 需要能够回答“某个请求对应哪个决策、哪个审批、哪个执行、哪个结果”这一类问题。
5. 事件顺序必须能证明执行前/执行后、拒绝前/拒绝后，以及审批与实际调用是否一致。
6. 时钟偏移、日志滞后、重复落库和时间回拨必须被识别并作为审计风险。
7. 对跨服务事件，必须定义统一时间源以及时间同步策略。

### 审计证据

- 时间同步策略、日志处理器配置、事件关联字段样本。
- 跨服务事件时间线复盘记录。

### 验证测试

- 模拟时钟偏移、重复事件、时间回拨和跨服务重放，验证日志能否识别异常。
- 检查请求和审批关联是否能从日志直接回溯。

## 6.5 检查项 C：日志真实性、不可篡改与访问控制

### 需求

1. 审计日志应来自可信执行组件，并且必须能证明其未被后续伪造、修改或覆盖。
2. 日志写入、访问、删除、归档和转储都必须受权限控制。
3. 应区分“日志生成者”和“日志管理员”；日志管理员不能无条件覆盖安全事件。
4. 需要对日志修改和删除行为进行审计，并保留相应记录。
5. 对于高风险系统，应考虑使用签名、哈希、WORM、不可变存储或等价机制，确保日志完整性。
6. 日志访问权限必须按最小权限原则授权；普通用户和开发者不能随意查询敏感审批/授权日志。
7. 任何第三方监控组件、代理或中间件都不能绕过日志完整性要求而替代人工审核。

### 审计证据

- 日志权限模型、访问控制策略、日志签名/哈希或不可变存储方案。
- 日志变更和删除事件审计记录。

### 验证测试

- 模拟日志覆盖、修改或删除请求，验证是否被拦截并记录。
- 检查日志访问控制是否能区分管理员、开发和只读审计人员。

## 6.6 检查项 D：日志脱敏、保留与归档

### 需求

1. 日志中不能直接记录密码、密钥、令牌、敏感数据内容或未脱敏的业务机密。
2. 日志的保留策略必须与风险、合规和追溯需求一致。
3. 数据保留期限、归档、压缩、加密传输和恢复流程都必须明确。
4. 对于存档和冷备份，应确保其同样具备访问控制和完整性保护。
5. 日志归档不能在保留期限内失去可审计性；归档后的日志仍应可搜索、验证和关联。
6. 归档和恢复流程必须保留操作证据，并能证明恢复过程没有伪造事件。

### 审计证据

- 日志保留政策、脱敏规则、归档方案、恢复记录。
- 归档文件的完整性校验结果。

### 验证测试

- 触发带敏感字段的日志事件，确认其被脱敏。
- 验证旧日志归档后仍可按要求检索和验证。

## 6.7 检查项 E：警报、事件关联、处置与复盘

### 需求

1. 安全事件日志必须能支持告警、事件关联和复盘，不仅支持存档。
2. 告警规则必须可关联到具体事件类型、来源、对象、风险级别和策略版本。
3. 事件日志应能证明某个告警是否由哪个请求触发、是否被确认、是否被处置、处置后是否恢复正常。
4. 多个相关事件（例如拒绝、审批缺失、外发尝试、日志泄露）应可按请求或会话进行串联。
5. 对误报与漏报需要设计复盘流程，并保留原因与修正记录。
6. 处理过程必须可追踪到责任人、时间和结果，而不是靠口头告知或离线沟通。

### 审计证据

- 事件关联链路、告警规则、告警处理记录、复盘报告。

### 验证测试

- 从一条告警事件出发，验证是否能串联到对应的请求、审批、拒绝或执行记录。

## 6.8 检查项 F：日志的运行时可靠性和恢复性

### 需求

1. 日志组件本身应具备容错能力，包括崩溃重启、网络中断、磁盘满、写入失败和队列积压的处理路径。
2. 日志记录失败必须被检测并上报，否则系统不能声称日志完整。
3. 对日志丢失、重试失败、异步写入时的潜在丢事件问题，必须有说明和治理策略。
4. 若日志系统不可用，必须明确影响范围以及安全措施（例如阻断高风险动作、切换到更保守模式）。
5. 日志恢复后，需可验证恢复前后事件的一致性和可追溯性。

### 审计证据

- 日志组件监控、写入失败告警记录、恢复步骤和验收记录。

### 验证测试

- 模拟日志写入失败、服务重启和恢复后验证事件能否继续追踪。

## 6.9 建议发现代码

- `LOG_MISSING`：关键事件无日志。
- `LOG_INCOMPLETE`：关键字段缺失或状态不一致。
- `TIME_INVALID`：时间戳缺失、时区缺失、时间回拨或数字错误。
- `EVENT_NOT_LINKED`：请求、会话、审批、执行和结论无法关联。
- `LOG_TAMPERED`：日志被修改、删除或覆盖。
- `LOG_SECRET_LEAK`：日志中出现秘密或敏感数据。
- `LOG_RETENTION_MISSING`：保留期限或归档策略未定义。
- `LOG_RECOVERY_UNVERIFIED`：日志恢复后无法证明完整性。
- `ALERT_NOT_TRACEABLE`：告警无法回溯到具体事件。
- `AUDIT_SYSTEM_UNRELIABLE`：日志系统本身不具备必要的可靠性或可用性。

## 6.10 后续 Python 包实例化需求

### 配置对象

后续 `AuditPolicy` 或独立审计配置中应支持：

- 日志字段要求、强制字段白名单和事件类型定义；
- 请求/会话/审批/策略版本关联字段；
- 最低时间精度与时区要求；
- 日志脱敏规则和保留期限；
- 告警事件类型、关联规则和处置状态；
- 日志可信性检查：签名、不可变存储、访问控制等。

### 输入事件

日志审计应处理标准化后的事件记录，而不是只接收随机文本。输入至少应包含：

- `timestamp`
- `event_id` / `request_id`
- `agent_id`
- `operation_type`
- `decision`
- `resource`
- `policy_version`
- `approval_ref`
- `execution_status`
- `reason_code`

### 输出要求

每条发现应记录：

- 发现代码；
- 严重性；
- 事件引用；
- 请求/会话链路；
- 相关策略版本和审批引用；
- 简述原因；
- 建议整改和责任人。

### 最小测试用例

1. 关键事件缺失时报告 `LOG_MISSING`。
2. 时间戳缺失或时间回拨时报告 `TIME_INVALID`。
3. 事件无法关联到请求或执行结果时报告 `EVENT_NOT_LINKED`。
4. 日志被修改或覆盖时报告 `LOG_TAMPERED`。
5. 日志中出现密钥/令牌/敏感数据时报告 `LOG_SECRET_LEAK`。
6. 无保留策略或归档策略缺失时报告 `LOG_RETENTION_MISSING`。
7. 告警无法回溯到事件时报告 `ALERT_NOT_TRACEABLE`。
8. 日志系统不可用或恢复无验证记录时报告 `AUDIT_SYSTEM_UNRELIABLE`。

## 6.11 本条验收标准

审计与日志审计模块满足以下要求后即可进入下一阶段：

- 关键事件覆盖齐全，且可关联到请求、审批、策略和执行状态。
- 日志具备可信写入、访问控制、不可篡改或等价保护机制。
- 日志字段、时间戳和保留策略清晰定义。
- 可追踪告警、处置和复盘过程。
- 文件、事件和错误日志中不存在未脱敏的秘密或敏感内容。

# 7. 升级性、适应性与安全治理审计

## 7.1 目标与边界

确认 Agent 安全框架不仅在当前系统中可用，而且具备持续修复、持续更新、持续评估和持续治理能力，能够随着新威胁、新技术和新业务场景持续增强安全控制，而不是仅停留在一次性配置或单次审计。

本章关注“系统治理能力”，包括版本维护、安全更新、适应性、制度流程、持续审查和风险管理闭环。

## 7.2 治理信任边界

审计前应明确：

- 安全策略和模型何时更新、谁审批、如何部署和回滚。
- 是否有定期风险评估、漏洞管理和渗透测试流程。
- 是否支持不同 Agent、不同环境和不同任务的安全适配。
- 是否存在新增功能或新工具时，安全控制未同步补足的风险。
- 组织如何处理安全事件、紧急修复和事后复盘。

## 7.3 检查项 A：更新机制、补丁与版本治理

### 需求

1. Agent 安全框架必须定义版本、变更记录、发布流程和回滚方法。
2. 安全修复必须有机制保证及时跟踪、审批、部署和验证。
3. 关键组件（策略、证书、工具网关、审计组件、模型接口等）都需要明确更新流程和责任人。
4. 应定义高危漏洞的处理 SLA 和升级优先级。
5. 发现漏洞后，必须可证明是修复了根因、不是仅增加监控或删除日志。
6. 更新过程必须保留因果链：变更原因、版本号、审批、验证、部署和回滚。

### 审计证据

- 发布策略、版本记录、补丁记录、回滚记录、漏洞修复状态。

### 验证测试

- 模拟漏洞修复和回滚流程，验证变更链路完整。

## 7.4 检查项 B：适应性、扩展性与环境隔离

### 需求

1. 安全框架应适应不同 Agent 角色、不同工具集和不同部署环境。
2. 不能以一个固定规则强行覆盖所有场景，否则容易出现误判或越权。
3. 开发、测试、生产环境必须隔离，并明确哪些策略和数据可跨环境使用。
4. 新增工具或新外部服务时必须重新做风险评估和权限审核。
5. 需要支持基于环境、租户、任务类型和风险级别的策略差异化。
6. 适应性要求不仅是“能配置”，还要验证“配置后生效”。

### 审计证据

- 环境隔离策略、任务环境差异配置、工具接入和风险评估记录。

### 验证测试

- 验证跨环境凭据、策略和数据边界是否隔离。

## 7.5 检查项 C：安全治理、合规和持续评估

### 需求

1. 组织应定期检查安全框架的有效性，而不是一次性发布后不再维护。
2. 要有安全复查、漏洞管理、审计复盘和政策更新流程。
3. 高风险变化必须触发风险评估和治理审查。
4. 对合规要求、角色责任和制度流程必须有明确说明。
5. 安全治理要覆盖人、流程、技术和证据链的闭环。

### 审计证据

- 安全评审报告、风险登记、漏洞跟踪和治理流程记录。

### 验证测试

- 模拟新工具接入、风险升级和治理流程触发，验证是否有相应评估和审批。

## 7.6 检查项 D：安全事件响应与持续改进

### 需求

1. 安全事件后必须进行快速响应、影响评估、止损和复盘。
2. 需要保留事前、事中和事后证据，形成闭环学习。
3. 处理结果必须反映在评审、策略和培训中。
4. 需要定义如何从一次问题中改进架构、流程和监控逻辑。
5. 不能仅修复单一症状而不修复根因。

### 审计证据

- 事件响应记录、复盘报告、整改计划和回访记录。

### 验证测试

- 模拟一次安全事件，验证从识别到修复再到治理更新的链路是否完整。

## 7.7 建议发现代码

- `GOVERNANCE_MISSING`
- `UPDATE_CHAIN_INCOMPLETE`
- `ROLLBACK_MISSING`
- `ENVIRONMENT_ISOLATION_BREACH`
- `ADAPTIVE_POLICY_UNVERIFIED`
- `SECURITY_REVIEW_OVERDUE`
- `INCIDENT_RESPONSE_INCOMPLETE`
- `CONTINUOUS_IMPROVEMENT_MISSING`

## 7.8 后续 Python 包实例化需求

- 扩展策略配置为支持版本、更新、回滚和治理状态。
- 为审计器增加“治理检查”能力，如更新证据、复查项和修复状态。
- 输出要区分：当前控制有效、治理缺失、修复未完成、无法验证。
- 最小测试应覆盖：版本变更、回滚、环境隔离、风险评估和事件复盘。

## 7.9 本条验收标准

- 能按版本、治理和修复闭环维护安全控制。
- 具有适应新环境和新风险变化的能力。
- 能在持续评估和事件复盘中改进安全策略。
- 能清晰证明治理过程和责任链条。
